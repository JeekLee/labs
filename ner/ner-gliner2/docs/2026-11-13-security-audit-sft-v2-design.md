# 군부대 보안 감사 온톨로지 SFT 실험 설계 v2 (1단계 재시작)

v1(`2026-11-13-security-audit-sft-design.md`)의 시험 실행 결과와 리뷰를 반영해 데이터와 구조를 처음부터 다시 만든다. v1에서 바뀌지 않은 결정(SFT, 가상 데이터, 통합 어댑터, 2단계 특화 어댑터, 커밋 규칙 등)은 v1 문서를 따른다. 공개 서식 조사 결과는 v1 문서의 「참고 자료: 공개된 보안 업무 서식」에 있다.

## v1에서 드러난 문제

- 평가 데이터의 사람 외 엔티티 표면형 91%가 학습 데이터와 같았다(엔티티 사전 공유). 엔티티 점수가 부풀려졌다.
- 문서가 모두 정형화된 보고 문서였고, 관리대장도 표가 아닌 서술형으로 쓰인 경우가 많았다(반출입 대장 17개 중 표 7개).
- 관계 오답의 절반이 같은 사람·대상 쌍에 열람·반출·관리 책임을 함께 붙이는 오류였다.
- 선택형 필드는 정답 단어가 본문에 적혀 있는지에 좌우됐다.

## 사용자가 정한 것 (v2)

- **문서 구성**: 실제 감사에서 확인하는 문서는 대부분 표 형식의 관리대장이다. 결과보고서·경위서는 요약 문서로 두고, 나머지는 공개 서식을 따른 관리대장으로 만든다.
- **관리대장 형식**: Markdown 표. 실제로는 한글·PDF로 오는 경우가 많지만 이번 실험에서는 표 구조를 유지한 Markdown으로 한다.
- **GLiNER의 역할**: 부대마다 열 이름과 형식이 다르므로, 같은 뜻을 같은 필드·관계로 읽어 내는 일. 이상 기록 판정은 GLiNER가 아니라 이후 단계의 LLM이 한다(이번 실험 범위 밖).
- **행 하나 = 기록 노드**: 관리대장의 행은 기록 노드(반출 기록, 열람 기록 등)로 만들고, GLiNER가 구조화 레코드 추출로 필드를 채운다. 반출자·승인자·매체 같은 역할은 기록 노드의 필드(역할 선)이다.
- **추상화 수준**: 4계층으로 나눈다.
  - L1 공통 엔티티
  - L2 공통 역할·지속 관계
  - L3 기록 유형별 필드
  - L4 기관별 표현 변형. L4는 스키마로 다루지 않고 데이터 변형으로 다룬다.
- **대장마다 레코드 타입을 따로 둔다**: 뜻이 겹치는 역할(승인자, 확인자 등)만 이름과 설명을 통일한다.
- **자격 증명 값 제외**: 비밀번호·PIN·암호 키 값은 추출하지 않으며, 가상 데이터에서도 `****`로 가린다.
- **표 입력 단위**: 행마다 대장 정보 한 줄(문서 제목, 부대, 관리책임자 등 표 위의 공통 정보) + 평탄화한 머리글 + 데이터 행 하나를 넣는다.
- **공개 서식 기반 합성**: 조사한 공개 서식의 열 구성을 따라 합성 데이터를 만들고, 그 데이터로 학습·평가 셋을 새로 만든다.
- **폴더 구조를 정리한다.**

## 목표 / 비목표

- 목표:
  - 관리대장 행의 기록 레코드 필드, 서술 문서의 엔티티·관계·사건 레코드를 정답지 대비 측정한다.
  - **학습에 없던 이름**과 **학습에 없던 열 이름 변형**에서의 성능을 따로 측정한다.
- 비목표: 이상 판정, 한글·PDF 변환, 상호참조, 2단계 특화 어댑터, 머리글 없는 입력 조건(이번에는 제외).

## 온톨로지 v2

### L1 공통 엔티티 (추출 대상)

v1의 11타입을 유지한다: Person, Position, Unit, Organization, Facility, Credential, ClassifiedDocument, StorageMedium, InformationSystem, Regulation, Inspection. 표기 규칙도 v1과 같다(Person은 계급 포함, 직책은 Position).

### L2 공통 역할과 지속 관계

- **공통 역할**: 기록 레코드의 역할 필드 이름. 여러 대장에서 같은 이름·설명을 쓴다.
  - 행위자 계열: 반출입자, 대출자, 열람자, 출입자, 사용자, 인가 대상자
  - 승인·확인 계열: 승인자, 확인자, 입회자, 보관책임자, 처리자, 관리책임자
- **지속 관계(JointIE)**: BELONGS_TO, HOLDS_POSITION, POSITION_OF, HOLDS, RESPONSIBLE_FOR, LOCATED_AT. 칸 안(`장지후 병장(정보통신대대)`), 비고 칸, 서술 문서에서 뽑는다.
- **v1 관계의 정리**: ACCESSED, CARRIED_OUT, STORED_ON, INSPECTED처럼 특정 행위를 나타내는 관계는 관리대장에서는 기록 레코드의 역할 필드로 표현한다. 서술 문서에서는 v1처럼 관계 추출로 둔다.
- **요약 관계**: 직접 관계(`반출입자 -CARRIED_OUT→ 매체`)가 필요하면 기록 노드에서 규칙으로 계산한다. GLiNER 추출 대상이 아니다.

### L3 기록 레코드 (관리대장별)

공개 서식에서 고른 대장과 기록 레코드(필드는 서식의 열을 따른다. 최종 목록은 구현 시 확정).

| 영역 | 대장 (공개 서식) | 기록 레코드 | 주요 필드 |
|---|---|---|---|
| 문서 | 비밀관리기록부 (A 별지20) | document_entry | 관리번호, 접수일, 생산처, 비밀등급, 건명, 보관장소, 처리방법, 처리일자, 처리자, 확인자 |
| 문서 | 비밀대출부 (A 별지23) | loan | 관리번호, 비밀등급, 건명, 대출자, 대출일자, 반납일자, 보관책임자 |
| 문서 | 비밀열람기록전 (A 별지24) | reading | 관리번호, 일시, 열람자, 인가등급, 열람목적 |
| 인원 | 비밀취급 인가대장 (A 별지7) | clearance | 인가번호, 인가 대상자, 소속, 인가등급, 인가일, 해제일, 해제사유 |
| 인원 | 비밀보관책임자 명부 (A 별지22) | custodian | 보관책임자, 소속, 인가등급, 정·부 구분, 임명일, 해제일 |
| 시설 | 통제구역 출입자명부 (A 별지29) | entry | 일자, 출입시간, 퇴청시간, 용무, 출입자, 입회자 |
| 시설 | 보안점검표 (A 별지30) | daily_check | 장소, 점검일자, 점검 항목 상태, 점검시각, 점검자, 특이사항 |
| 정보통신 | 저장매체 관리대장 (C 별지6) | medium_entry | 등록번호, 매체형태, 등급, 수령일자, 수령 확인관, 반납일자, 반납 확인관, 불용처리 방법 |
| 정보통신 | 휴대용 저장매체 반출·입 대장 (D, 국정원 지침 별지4) | medium_transfer | 장비명, 관리번호, 사용자, 용도, 점검사항, 반출입 일시, 구분, 확인자 |
| 정보통신 | 정보시스템 관리대장 (D·E·F) | system_entry | 소속, 취급자, 종류, 관리번호, 설치장소 |

서술 문서의 레코드(incident, finding, action)는 v1을 유지한다.

### L4 기관별 변형 (데이터로만 다룸)

부대(가상)마다 같은 대장의 표현을 바꾼다.
- 열 이름 동의어(예: 사용자/반출자/대여자, 확인자/확인관/확인 서명)
- 열 순서, 한 칸에 여러 정보 묶기(`소속·직급·성명`)
- 날짜 형식(`2026. 4. 7.` / `26-04-07` / `4.7.`)
- 비고 칸의 자유 서술

## 데이터 v2

1. **엔티티 사전을 학습용과 평가용으로 나눈다.** 이름, 부대, 시설, 매체 관리번호, 문서 건명, 정보체계, 규정을 분리한다. 평가 문서에는 학습에 없던 표면형을 쓴다.
2. **서식 정의 파일**: 대장마다 정규 열 목록, 기관별 변형(열 이름 동의어, 순서, 묶음 칸, 날짜 형식)을 정의한다. 학습에 쓰지 않는 변형을 평가 전용으로 남긴다.
3. **시나리오**: v1처럼 시나리오 그래프를 먼저 만든다. 사건 유형에 맞는 대장을 배정한다(예: 저장매체 무단 반출이면 반출·입 대장과 저장매체 관리대장).
4. **관리대장은 코드로 렌더링한다.** 시나리오와 사전으로 정상 행 여러 개와 사건 관련 행을 만들고, 기관 변형을 적용해 Markdown 표로 쓴다. 정답(엔티티 위치, 레코드 필드, 지속 관계)은 렌더링하면서 정확히 기록된다. 비고 칸의 자유 서술 일부는 서브에이전트가 쓴다.
5. **서술 문서**(결과보고서, 경위서, 조치 이행 현황 등)는 v1처럼 서브에이전트가 작성 지시에 따라 쓰고, 검증기를 통과시킨다. 작성 지시에 머리글의 점검 대상·작성자 소속 같은 관계도 정답으로 표시하라는 규칙을 추가한다.
6. **선택형 필드**: 정답 선택지가 본문에 적힌 레코드와 적히지 않은 레코드를 모두 만들고, 두 경우를 따로 집계한다.

## 평가

- 조건: zero-shot, 통합 어댑터(v1과 같은 LoRA 설정).
- 지표:
  - 엔티티 F1: 학습에서 본 표면형과 처음 보는 표면형을 나눠서 잰다.
  - 관계 F1: 서술 문서와 지속 관계를 잰다.
  - 기록 레코드 필드 F1: 대장별, 그리고 학습에서 본 열 변형과 처음 보는 열 변형을 나눠서 잰다.
  - 사건 레코드 필드 F1과 선택형 정확도: 정답 단어가 본문에 있는 경우와 없는 경우를 나눠서 잰다.
- 목표 점수는 v1과 같다(엔티티 0.90, 관계 0.80, 레코드 필드 0.80, 선택형 0.90). 미달 시 대응은 결과를 보고 정한다.

## 설계자 판단 (리뷰 후 결정)

- **v1 산출물**: v1 시험 실행 전체를 커밋 `9f18cde`로 고정했다(사용자 결정). v2는 같은 위치에서 다시 만들어 덮어쓰고, 코드는 `config/security_audit/` 패키지로 옮긴다. v2 노트북의 결론에 v1 시험 수치(`9f18cde`의 `security_audit_sft_pilot.json`)와 짧게 비교한다.
- **열로 표현된 지속 관계도 정답에 넣는다.** 같은 사실은 서식이 달라도 같은 정답이어야 하므로(L4 원칙), 관리대장의 행에서도 지속 관계를 관계 정답으로 기록한다.
  - 성명과 소속이 같은 행에 있으면 BELONGS_TO
  - 인가대장의 행은 HOLDS
  - 보관책임자 명부의 행, 정보시스템 취급자, 표 위의 관리책임자는 RESPONSIBLE_FOR
  - 설치장소는 LOCATED_AT

  묶음 칸(`장지후 병장(정보통신대대)`)과 비고 칸도 같다. 렌더러가 이 관계를 정답으로 함께 기록하고, 관계 F1은 대장 행과 서술 문서를 나눠서 잰다.
- **평가 데이터 구성(처음 보는 것과 본 것을 모두 측정)**:
  - 평가 대장의 엔티티는 약 절반을 평가 전용 사전에서, 나머지를 학습 사전에서 가져온다.
  - 열 변형은 대장마다 학습용 2~3종과 평가 전용 1종을 둔다. 평가 대장의 약 절반은 학습용 변형, 나머지는 평가 전용 변형으로 렌더링한다.
  - 평가 전용 변형은 열 이름뿐 아니라 묶음 칸, 열 순서, 날짜 형식도 학습 변형과 다르게 한다.
- **대장의 엔티티 표기 규칙**:
  - Person: 같은 칸에 계급과 성명이 함께 적혀 있으면 적힌 그대로 계급 포함(`병장 장지후`, `장지후 병장`). 계급이 별도 열이면 성명 칸만 Person이고, 계급 칸은 엔티티가 아니다.
  - 묶음 칸(`정보통신대대 병장 장지후`): 부대는 Unit, 계급+성명은 Person으로 따로 표시한다.
  - 역할 필드의 값은 칸 전체가 아니라 Person 범위이다.
  - 인물은 군 계급과 군무원(예: `7급 군무원`)만 쓴다.
  - StorageMedium 엔티티는 관리번호(`USB-118`)이고, 장비명·매체형태(`업무용 USB`)는 기록 필드 값이다.
  - ClassifiedDocument 엔티티는 건명이고, 관리번호·비밀등급은 기록 필드 값이다.
- **규모와 진행**:
  - 시나리오 60개(학습 45, 평가 15)로 한 번에 진행한다. 관리대장은 코드로 렌더링하므로 비용이 작고, 서술 문서(시나리오당 1~2개)만 서브에이전트가 쓴다.
  - 전체 생성 전에 시나리오 3개로 렌더링·변환·채점을 확인하는 스모크 단계를 둔다.
  - 학습은 CPU에서 수십 분이 걸릴 수 있다.
- **기록 유형은 알려진 것으로 본다.** 대장 제목에서 기록 레코드 종류를 정하고, 행마다 해당 스키마 하나로 추출한다. 처음 보는 제목의 대장 유형을 판정하는 일은 이번 범위 밖이다.
- 기록 레코드의 필드는 공개 서식의 열에서 감사에 의미 있는 것만 고른다. 생년월일·주민등록번호 등 개인정보 열은 제외한다.
