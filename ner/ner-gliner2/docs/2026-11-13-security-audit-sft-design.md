# 군부대 보안 감사 온톨로지 SFT 실험 설계 (1단계, experiments/04)

## 목적

GLiNER2를 도메인 정답 데이터로 지도 미세조정(SFT)했을 때, **도메인 온톨로지(엔티티·관계·사건 레코드)를 정답지 대비 얼마나 정확히 추출하는지** 측정한다.

시나리오는 가상의 군부대 보안 감사이다. 감사관이 부대의 각종 문서와 기록(점검 보고서, 경위서, 대장, 회의록 등)을 분석해 지식 그래프에 넣고 감사에 활용하는 상황을 가정한다. 보안 감사 영역은 인원보안·문서보안·시설보안·정보통신보안 네 가지이며, 1단계는 네 영역의 공통 지식을 담은 **통합 어댑터**를 만든다.

배경: `notebooks/02`와 `experiments/03`에서 KLUE(사람·기관·장소 3타입, 엔티티만)로 SFT와 증류를 실험했다. 이번에는 사용자가 정의한 도메인 온톨로지 전체(다수의 엔티티 타입, 관계, 사건 레코드)로 범위를 넓힌다.

## 사용자가 정한 것

- **방식**: SFT. 문장과 정답을 함께 주는 지도 미세조정(LoRA).
- **시나리오**: 가상의 군부대 보안 감사. 입력은 이슈·회의록 같은 문서와 기록.
- **영역**: 인원·문서·시설·정보통신 보안. 네 영역은 공통으로 쓰이므로 **하나의 통합 온톨로지와 통합 어댑터**로 학습한다.
- **단계**: 2단계로 나눈다. 1단계(본 문서)는 통합 어댑터, 2단계는 통합 어댑터에서 군종·수검 기관별 **특화 어댑터**를 만드는 실험이다. 2단계는 별도 설계로 다루되, 1단계 데이터와 코드는 2단계에서 재사용할 수 있게 만든다.
- **데이터**: Claude가 전부 가상으로 만든다. 개인 연구용 NER 어댑터 학습 목적이며, 사용자는 약관상 문제가 없다고 판단했다.
- **GLiNER가 맡는 일** (방식 B):
  1. 이름 있는 엔티티 추출 (인원, 부대, 시설, 매체, 문서, 정보체계, 규정 등)
  2. 엔티티와 엔티티 사이의 관계 추출
  3. 사건 레코드 채우기: 사건 유형 분류 + 역할 필드(관련자, 매체, 대상 문서, 장소, 위반 규정 등)
  - 사건·발견 사항·조치 노드는 문장 속 구절로 추출하지 않고 **문서 단위로 생성**한다(경위서 1건 = 사고 1건, 점검표 항목 1개 = 발견 사항 1개). GLiNER는 그 노드의 유형과 역할 필드를 채운다.
- **판단 기준**: 정답지 대비 점수. 목표에 못 미칠 경우의 대응은 미리 정하지 않고, 결과를 보고 원인을 분석한다.
- **규모**: 약 30개 시나리오로 먼저 시험 생성해 정답 일관성과 학습 가능성을 확인한 뒤 전체 규모로 늘린다.
- **2단계 준비**: 1단계 데이터에는 보안 영역 태그만 붙이고 군종 구분 없이 공통 용어로 쓴다. 2단계는 군종·기관별 데이터를 새로 만들고 1단계의 온톨로지·엔티티 사전·코드를 재사용한다. 1단계 통합 어댑터를 기본 모델에 병합한 뒤 그 위에 특화 LoRA를 학습한다.
- **계급과 직책**: 군 문서는 계급·직책으로 사람을 가리키는 경우가 많으므로, 계급은 Person 범위에 포함하고 직책은 별도 엔티티 타입 Position으로 둔다(아래 표기 규칙).

## 목표 / 비목표 / 실패 조건

- 목표:
  - 학습 전(zero-shot)과 통합 어댑터를 같은 평가 데이터로 비교한 점수 표(엔티티·관계·레코드 필드·사건 유형).
  - 타입별·관계별·문서 종류별·영역별 점수와 오류 분석.
  - 문서 → 그래프 변환 예시(정답 그래프와 추출 그래프 나란히).
- 비목표: 2단계 특화 어댑터, 직책 언급과 인물의 상호참조, LLM 추출 비교, 실제 군 문서 사용, 지시어·문서 간 상호참조 해결, 설명형 구절(방식 A)의 본격 실험(아래 보조 측정만).
- 실패 조건(동작해도 의미 없는 경우):
  - 학습·평가 문서가 같은 시나리오나 같은 문장 틀을 공유해 점수가 부풀려지는 경우.
  - 정답 표시가 일관되지 않아(같은 표현이 문서마다 다른 타입·범위) 점수가 모델이 아니라 데이터 품질을 재는 경우.
  - 실존 부대명·인원·비밀 내용처럼 보이는 정보가 데이터에 섞이는 경우.

## 성공 기준 (설계자 제안, 사용자 수용)

| 평가 대상 | 지표 | 목표 |
|---|---|---|
| 엔티티 | 범위+타입 정확 일치 F1 (타입별, 전체) | 0.90 |
| 관계 | (출발, 관계 타입, 도착) 정확 일치 F1 | 0.80 |
| 사건 레코드 필드 | 필드 값 정확 일치 F1 (필드별, 전체) | 0.80 |
| 사건 유형 | 분류 정확도 | 0.90 |

정답지를 같은 작성자가 만든 가상 데이터이므로 실제 문서보다 점수가 높게 나올 수 있다. 이 점을 결론에 명시한다. 학습 전 GLiNER(레이블 설명만 준 zero-shot) 점수를 함께 보고해 학습 효과를 보인다.

## 온톨로지 (설계자 초안)

create-context-graph의 온톨로지 YAML 형식을 따른다(`inherits: _base`, `entity_types[].label/pole_type/subtype/properties`, `relationships[].type/source/target`). 파일: `config/domains/military-security-audit.yaml`. GLiNER 레이블은 YAML의 타입에서 생성하며, 레이블마다 한국어 설명을 붙인다.

### 엔티티 타입 (14)

| 타입 | pole_type | 주 영역 | 예 |
|---|---|---|---|
| Person | PERSON | 공통 | 김OO 상병, 상병 김OO, 김 상병 |
| Position | OBJECT (subtype ROLE) | 공통 | 보안담당관, 정보체계 관리자, 당직사관 |
| Unit | ORGANIZATION | 공통 | ○○사단 정보통신대대, 작전과 |
| Organization | ORGANIZATION | 공통 | 외부 협력업체, 상급 감사기관 |
| Facility | LOCATION | 시설 | 통제구역, 문서보관실, 출입통제소 |
| Credential | OBJECT | 인원 | 비밀취급인가, 출입증, 정보체계 계정 |
| ClassifiedDocument | OBJECT | 문서 | Ⅱ급 비밀 문서, 대외비 보고서 |
| StorageMedium | OBJECT | 문서·정보통신 | 보안 USB, 외장하드 |
| InformationSystem | OBJECT | 정보통신 | 내부망 단말, 업무 서버 |
| Regulation | OBJECT | 공통 | 저장매체 통제 규정, 출입 통제 지침 |
| Inspection | EVENT | 공통 | 정기 보안점검, 보안교육 |
| SecurityIncident | EVENT | 공통 | 문서 단위 생성 (추출 대상 아님) |
| Finding | OBJECT | 공통 | 문서 단위 생성 (추출 대상 아님) |
| CorrectiveAction | EVENT | 공통 | 문서 단위 생성 (추출 대상 아님) |

GLiNER의 **엔티티 추출 대상은 위 11개**(SecurityIncident·Finding·CorrectiveAction 제외)이다. Inspection은 "정기 보안점검"처럼 이름이 붙은 행사로 추출한다.

### 관계 타입 (17)

| 관계 | 출발 → 도착 | 추출 방식 |
|---|---|---|
| BELONGS_TO | Person → Unit | 관계 추출 |
| HOLDS_POSITION | Person → Position | 관계 추출 |
| POSITION_OF | Position → Unit | 관계 추출 |
| HOLDS | Person → Credential | 관계 추출 |
| RESPONSIBLE_FOR | Person → Facility, ClassifiedDocument, StorageMedium, InformationSystem | 관계 추출 |
| ACCESSED | Person → Facility, InformationSystem, ClassifiedDocument | 관계 추출 |
| CARRIED_OUT | Person → StorageMedium, ClassifiedDocument | 관계 추출 |
| STORED_ON | ClassifiedDocument → StorageMedium, InformationSystem | 관계 추출 |
| LOCATED_AT | Facility, InformationSystem, StorageMedium → Facility, Unit | 관계 추출 |
| INSPECTED | Inspection → Unit, Facility, InformationSystem | 관계 추출 |
| INVOLVED_IN | Person → SecurityIncident | 사건 레코드 필드 |
| OCCURRED_AT | SecurityIncident → Facility, InformationSystem | 사건 레코드 필드 |
| VIOLATES | SecurityIncident, Finding → Regulation | 사건 레코드 필드 |
| IDENTIFIED | Inspection → Finding | 문서 구조 + 레코드 필드 |
| CONCERNS | Finding → Person, Facility, ClassifiedDocument, StorageMedium, InformationSystem | 사건 레코드 필드 |
| REMEDIATES | CorrectiveAction → Finding, SecurityIncident | 문서 구조 |
| ASSIGNED_TO | CorrectiveAction → Person, Unit | 사건 레코드 필드 |

엔티티 사이의 관계 10개는 GLiNER 관계 추출(JointIE 스키마)로, 사건 노드에 연결되는 관계는 사건 레코드의 필드로 표현한다.

### 사건 레코드 (구조화 추출)

| 레코드 | 필드 |
|---|---|
| incident (SecurityIncident) | 유형(선택형), 관련자, 매체, 대상 문서, 장소, 위반 규정, 일자 |
| finding (Finding) | 영역(선택형: 인원·문서·시설·정보통신), 대상(직책 포함), 위반 규정 |
| action (CorrectiveAction) | 조치 내용 요약(선택형 유형), 담당자·담당 부대, 기한 |

사건 유형의 선택지 예: 저장매체 무단 반출, 비인가 출입, 비밀문서 관리 소홀, 계정·권한 관리 위반, 보안교육 미이수, 인가 만료자 접근. 최종 목록은 구현자가 온톨로지와 함께 확정한다.

## 데이터 (설계자 제안: 시나리오 우선 방식)

1. **엔티티 사전**: 가상의 부대(군종 구분 없이 공통 용어), 계급·이름, 시설·구역, 매체 일련번호, 문서명, 정보체계명, 규정명을 만든다. 실존 부대명·인명·실제 비밀 내용은 쓰지 않는다. 보안 규정은 공개된 일반 수준의 표현만 쓴다.
2. **시나리오 그래프**: 사건 하나를 정답 그래프로 먼저 만든다(관련 인원, 매체, 문서, 장소, 위반 규정, 발견 사항, 조치와 그 관계). 네 영역과 사건 유형이 고르게 분포하도록 시나리오를 배분한다.
3. **문서 작성**: 시나리오 하나를 여러 종류의 문서로 쓴다. 문서 종류: 보안점검 결과보고서, 보안사고 경위서, 출입기록 점검 결과, 저장매체 반출입 대장, 비밀문서 관리대장 점검표, 보안대책 회의록, 보안교육 결과, 정보체계 접근권한 점검 결과. 작성하면서 엔티티를 표시하고, 관계·레코드 정답은 시나리오 그래프에서 가져온다(문서에 실제로 서술된 것만 정답으로 남긴다).
4. **정답 형식**: 문서(또는 문단) 단위로 엔티티 범위(start/end/타입), 관계 (head, 관계, tail), 레코드 필드 값을 저장한다. GLiNER2 `InputExample`의 `entities`, `relations`, `structures`(+선택형 필드)로 변환한다. 모든 엔티티 레이블을 빈 목록 포함으로 선언하고, Kiwi 경계와 맞지 않는 범위는 제외 비율을 기록한다.
5. **검증**: 표시한 범위가 원문과 일치하는지, 같은 표면형이 문서마다 같은 타입으로 표시됐는지 자동 검사한다.
6. **분할**: 평가 데이터는 학습에 쓰지 않은 시나리오로 만든다. 평가 데이터의 일부는 학습에 없는 문서 종류(예: 회의록 계열 하나를 평가 전용으로)와 별도 작성 지시로 만들어, 문체 암기의 영향을 따로 본다.

규모(설계자 제안): 먼저 약 30개 시나리오로 시험 생성·학습·평가를 한 번 돌린 뒤, 학습 시나리오 약 150개 × 문서 4~6종 → 문서 약 700~900개(문단 단위로 나누면 학습 예시 약 2,000개), 평가 시나리오 약 40개 → 문서 약 200개. 문서 작성은 서브에이전트로 나누어 병렬 생성한다.

## 실험 조건과 평가

| 조건 | 내용 |
|---|---|
| zero-shot | `fastino/gliner2.5-multi-v1` + Kiwi 분할기, 레이블 설명만 제공 |
| 통합 어댑터 | 같은 체크포인트·분할기 + LoRA SFT (엔티티·관계·레코드 동시 학습) |

- 학습 설정은 `notebooks/02`의 LoRA 설정을 출발점으로 한다(2 epoch, 배치 8, seed 42). 하이퍼파라미터 탐색은 하지 않는다.
- 엔티티는 `config/klue.py`의 정확 일치 채점과 오류 분류를 재사용·일반화한다.
- 관계는 JointIE 스키마로 추출해 (head 표면형, 관계, tail 표면형) 정확 일치로 채점한다.
- 레코드는 필드별로 값의 정확 일치(목록 필드는 원소 단위 F1), 선택형 필드는 정확도로 채점한다.
- 보조 측정(방식 A): 사건 서술 구절을 엔티티처럼 추출했을 때의 점수를 평가 데이터 일부에서 함께 기록한다. 학습에는 쓰지 않는다.

## 제약

- 로컬 macOS CPU에서 학습·평가한다. 외부 API는 쓰지 않는다(데이터는 Claude가 세션 안에서 생성).
- 모든 데이터는 가상이며 실존 부대·인원·비밀 내용을 포함하지 않는다.
- 커밋은 사용자가 요청할 때만 한다. 기존 노트북은 생성 스크립트로 다시 만들지 않는다.
- 예시의 사람 이름은 `JeekLee`를 쓸 수 있으나, 데이터의 인물은 다양한 가상 이름을 쓴다.

## 구현 전에 확인할 것

- GLiNER2 학습에서 엔티티·관계·구조화 레코드를 한 예시에 함께 넣었을 때 정상 학습되는지, 관계 학습 효과가 JointIE 추론에 반영되는지.
- 문서 길이와 GLiNER2 입력 길이 한도. 길면 문단 단위로 나눈다.
- 관계의 head/tail이 문자열이라 같은 이름이 여러 번 나올 때의 모호성.

## 설계자 판단 (리뷰 후 결정)

- **레코드 단위는 문서 구조로 주어진다(oracle).** 모든 문서는 레코드 단위가 드러나는 서식으로 작성한다. 경위서는 문서 전체가 사건 1건, 점검표·결과보고서는 번호가 붙은 발견 사항 항목, 조치 계획은 표의 행이 레코드 1개이다. GLiNER는 레코드의 개수와 경계를 찾지 않고, 주어진 레코드 단위 텍스트의 유형과 필드만 채운다. 따라서 레코드 매칭 단계는 없다. 레코드는 레코드 단위 텍스트로 학습·채점하고, 엔티티·관계는 문단 단위로 학습·채점한다(같은 문서에서 만든 두 종류의 예시).
- **온톨로지 YAML은 형식 규약으로만 따른다.** create-context-graph를 설치하거나 그 도구로 검증하지 않고, YAML을 읽는 작은 로더를 만든다. 1단계에서는 Neo4j에 적재하지 않으며, "문서 → 그래프" 예시는 정답 그래프와 추출 그래프를 나란히 보여주는 표·그림으로 만든다.
- **엔티티 표기 규칙(문서 작성 전에 확정).**
  - Person은 특정 개인을 가리키는 언급이며 **문서에 적힌 계급을 범위에 포함**한다(`김OO 상병`, `상병 김OO`, 성+계급 `김 상병`). 소속 부대명은 범위에서 뺀다. 계급은 정해진 목록이므로 필요하면 범위에서 규칙으로 분리한다.
  - Position은 직책 자체이다(`보안담당관`, `정보체계 관리자`, `당직사관`). `보안담당관 이OO 중사`는 Position `보안담당관` + Person `이OO 중사` + 관계 HOLDS_POSITION으로 표시한다. 직책만 나온 언급을 같은 문서의 특정 인물과 연결하는 일(상호참조)은 1단계 범위 밖이며, Position 노드로만 남긴다.
  - Unit은 공식 부대·부서명 전체(`○○사단 정보통신대대`)를 한 범위로 표시한다.
  - Inspection은 고유하게 특정되는 행사명(`2026년 1분기 정기 보안점검`)만 표시한다. 일반 명사(`보안교육`)는 표시하지 않는다.
  - 같은 표면형은 모든 문서에서 같은 타입으로 표시하며, 자동 검사로 강제한다.
- **보조 측정(방식 A)의 정답**: 평가 데이터의 경위서에 한해, 문서 작성 시 사건 행위를 서술한 절(주어 제외, "…를 반출" 같은 서술부)을 `incident_description` 범위로 함께 표시한다. 학습에는 쓰지 않는다.

- A, B, C의 서식은 PDF 원문에서 열 구성을 직접 확인했다.
